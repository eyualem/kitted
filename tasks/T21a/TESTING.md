## How the server is tested
`firebase/tests/api.test.ts` on the emulator (a real in-process handler, Firestore emulator, fake Gemini). Add `devices` to the collections cleared in `beforeEach`. A new request header `X-Kitted-Device: <id>` (16–64 characters: letters, digits, dashes). "Signs out" = a second `signUp()` (a new guest uid) sending the same device ID. Beta/free numbers are the ones already in `limits.ts`. The device document id is `sha256(deviceId)` as lowercase hex; its day lives at `devices/{hash}/usageDays/{day}`.

## Criteria
- **F10.1·a (the gap)** · a guest uses its day's checks on phone D; a new guest uid on D is refused the next new check with `429 {error:'limit', which:'checks'}` · how: server emulator · expect: refused with the same body as an account over its limit · must not: the new uid starting from zero · test: `api.test.ts` › `F10.1 · a new guest on the same phone is still refused (checks)` · red: the new guest's `read` on phone D answers 200 instead of 429 checks (the test fails reading the 200 stream as JSON in `expectLimit`).
- **F10.1·b** · the same for questions: after the day's questions on D, a new guest's next question is `429 limit` with `which:'questions'` · test: › `F10.1 · ... (questions)` · red: the new guest's 8th question answers 200 instead of 429 questions (same `expectLimit` failure).
- **F10.1·c (a phone is the unit, not the world)** · a new guest on a different phone D2 is untouched and passes · must not: refusing D2 · test: › `F10.1 · another phone is untouched` · red: `phoneTotal(D,'checks')` is 0, expected 1 (no phone record is written yet).
- **F10.1·d (retry on a counted check)** · on the same phone, a new uid calling again on a check id the phone already counted today is not a new check: it passes while the phone's day has no room for new ones, and counts no extra check · test: › `F10.1 · the same check id on the same phone isn't counted twice` · red: `phoneTotal(D,'checks')` is 0, expected 1 after the retry (nothing on the phone's day).
- **F10.1·e (no half-write)** · when the phone's day refuses, the new account's own day is not changed (nothing counted); when the account's day refuses, the phone's day is not changed · how: read the two day docs after the refusal · test: › `F10.1 · a refusal on either side counts nothing on the other` · red: the new guest's refused check answers 200, not 429 (`expectLimit` fails parsing the 200 stream).
- **F10.1·f (give back on both)** · a failed, timed-out or unfinished read gives the check back on the account's day and on the phone's day (a retry then passes) · test: › `F10.1 · a failed read gives the check back on both days` · red: `phoneTotal(D,'checks')` is 0, expected 1 after a new guest's good read (no phone day exists).
- **F10.1·g (the day cannot be moved)** · a new guest on the same phone that asks for a different time zone (`X-Kitted-Tz`) inside 20 h is still on the phone's own day, so the refusal stands; the phone's tz change is taken only after 20 h (same rule as L8) · test: › `F10.1 · a new guest cannot move the phone's day with a time zone` · red: `phoneDays(D)` is `[]`, expected `['2026-10-20']` (no phone day written).
- **F10.1·h (the header)** · a malformed device ID (too short, bad characters, over 64) → `400 {error:'badRequest', reason:'device'}` before anything is counted; no header → behaves as today (account only); with `server/config.requireDevice: true`, no header → `400 badRequest reason 'device'`; `requireDevice` missing or non-boolean means false · test: › `F10.1 · the device header` · red: a malformed device ID answers 200 instead of 400 `badRequest`/`device` (fails parsing the 200 stream).
- **F10.1·i (privacy: what is stored)** · the phone's document id is the sha256 hex of the ID, never the ID itself; no document under `devices/` and no log line (`log` entries) contains the raw ID; the only fields on the phone's documents are the day's counts, `ids`, `at` and the tz fields (`tz`, `tzChangedAt`): no uid, no text, no photo field · how: read every doc under `devices` with the Admin SDK and scan the log array · must not: the raw ID, the uid, any other field · test: › `F10.1 · the phone's record holds only a hash and counts` · red: no document under `devices/` (0, expected at least 1).
- **F10.1·j (the purge)** · the existing daily sweep of `usageDays` older than `USAGE_DAYS` also removes `devices/*/usageDays` days · how: `functions.test.ts` (existing sweep harness) · test: `functions.test.ts` › `F10.1 · the sweep also clears the phone's old days` · exists: bites via a deliberate bug (the sweep deletes only `usage/` days): `['2026-10-20','2026-10-28']` left, expected `['2026-10-28']`. Note: it passes today because the collection-group sweep already covers `devices/*/usageDays`.
- **F10.1·k (the same rules otherwise)** · L10: two accounts with no device header or different phones stay apart; the founder tier and `GET /v1/tier` answer as before (the tier route never counts) · test: existing L10 and tier tests keep passing (exists: bites via a deliberate bug) · exists: bites via a deliberate bug (every account's day stored at `usage/shared/...`): the new test `F10.1 · no header and other phones keep accounts apart; the tier route never counts` fails with 429 instead of 200. The old L10 test did NOT catch that bug (it reuses one check id, which passes as a hedge), so the new test is the real L10 guard.
- **F10.1·l (app)** · the app sends `X-Kitted-Device` on photo and ask calls: the same ID on every call; one is made and saved to the Keychain only when none exists; the ID is the same after a simulated sign-out (a new guest token, same Keychain) · how: jest (`--maxWorkers=2`) on `serverTransport` with a fake `fetch` and a fake Keychain · must not: a new ID per call or per guest · test: `app/src/__tests__/serverDevice.test.ts` › `F10.1 · the device ID is sent and stable across a sign-out` · red: the `X-Kitted-Device` header is `undefined` on every call (3 jest tests: the sign-out test, a Keychain ID already there, and calls that start together).
- **F10.1·m (privacy on the refused and failed paths)** · the raw device ID appears in no `log` entry and no response body on the 429 limit path (a check and a question), the 400 bad-header path (the bad value holds the raw text) and the 502 upstream-failure path · test: › `F10.1 · a refused or failed call never puts the raw device ID in a log line or a response` · exists: bites via two planted bugs (the raw ID added to the 429 limit log line; the raw ID added to a log line on the 400 path): the test fails on the log scan in both. Added after review (strengthened).
- **F10.1·n (give back what each day took)** · on the ask route the account and the phone can choose differently between a tap and a question; when such an ask fails or is unfinished, each day gets back exactly what it took, so both days' `taps` and `questions` equal their values before the call; a finished ask keeps what each took · how: set the days apart (the account's taps used up on phone D, then a fresh phone D2; and a new guest with tap room on phone D whose taps are used up) · test: › `F10.1 · a failed ask gives back what each day took when the account and the phone chose differently` · red: after a failed tap ask on the fresh phone D2, the phone's day shows `[taps, questions]` of `[1, 0]`, expected `[0, 0]` (the account's `took`, a question, was used on the phone, which had taken a tap). Added after review (strengthened).
