## Criteria
- **SB4.1a** · Photo backup is off after sign-in; with it off no photo is uploaded · how: unit (the backup engine over a recording file transport and the memory remote, a store with kept photos, `-send` copies and a cache file) · expect: signed in, setting absent → rows go up, `upload` is called 0 times and the file queue stays empty; setting `backup.photos = 'on'` → `upload` is called once per kept photo under `photos/`, `closet/`, `scans/` and never for a `-send` copy, a cache or a path outside the three folders; turning it off stops further uploads · must not: any upload while off, including a photo added after sign-in, a restore, or the app coming to the foreground.
- **SB4.1b** · With it off, no photo reaches Storage (the spec's emulator test) · how: emulator (the real storage transport and Firestore remote against the emulators, signed in as a non-anonymous user) · expect: a full sync with photos on his phone and the setting off leaves `users/{uid}/files/` empty in the Storage emulator; with it on the same photos land there · must not: a file under `users/{uid}/files/` while off.
- **SB4.1c** · The setting belongs to the account · how: unit · expect: the setting is a synced pref that a second phone pulls (`backup.photos` is in `KV_SYNCED`, not local); a restore to an account whose setting is on reports "photo step: skip", an account with it off or absent reports "photo step: show"; the step is offered once after a sign-in and not again on the next launch · must not: the photo step showing on a restore with the setting on.
- **SB4.2** · Another account can't read, list, write or delete his photos · how: emulator (rules test) · expect: with a photo at `users/A/files/photos/x.jpg`, user B's get, list, create, update and delete all fail; a signed-out client's fail; A's get/delete work; an anonymous (guest) user's own folder still follows the same rules · must not: any cross-account access.
- **SB4.3a** · Turning photo backup off deletes the backed-up photos from the server after the confirm · how: emulator (the new server job's exported function, like `deleteEverything`) + unit (the switch's logic over fakes) · expect: after the job, no object under `users/{uid}/files/` remains and another user's files are untouched; the Firestore docs (fits, closet rows) are untouched; in the app, confirm → job called once → setting off → photos on the phone untouched; Cancel → nothing called, setting stays on · must not: deleting before the confirm; deleting rows; touching another user's files.
- **SB4.3c** · Turning photo backup off and on again sends every kept photo once more (added round 3, reviewer defect 3) · how: unit (the backup over the memory remote and a recording file transport; `turnOffPhotoBackup` with a job that empties the server's folder) · expect: photos up with the setting on (4 uploads); turn off with the job ok (the setting is off, no row or queue entry still counts a photo as uploaded); rounds while off upload nothing; turn on, sync → `upload` is called again exactly once per kept photo (8 in all), the server has all 4 again, and a further round uploads nothing; a failed or offline turn-off leaves `syncRows` and `syncFiles` exactly as they were and a later round uploads nothing twice · must not: a photo left out of the second upload because its row still says it is on the server; the bookkeeping reset when the job failed.
- **SB4.3b** · Turning it off while offline or when the job fails changes nothing · how: unit · expect: the job rejects (offline, failed) → the setting stays `'on'`, the uploaded-files bookkeeping is unchanged, and the result says offline vs failed so a toast can show · must not: the switch flipping off with the server's copies still there.
- **SB5.1a** · Chat messages never reach the server · how: unit (sync schema + engine) and emulator (rules) · expect: `TABLE_POLICY.chat === 'local'`; `SYNCED_COLLECTIONS` has no `chatMessages`; a store with chat rows synced through the engine produces no `chatMessages` doc in the remote; a pulled account never overwrites or adds chat rows; `firestore.rules` refuse a `users/{uid}/chatMessages/{id}` write and read; the server's `SYNCED_COLLECTIONS` (functions) has no `chatMessages` · must not: any chat row, payload or text in any remote doc.
- **SB5.1b** · Name, age band, birth year, the under-18 lock and the other never-sent state never reach the server · how: unit (engine over a recording remote with a profile that has `name`, `ageBand`, `ageBandAt`, `birthYear`, height, build, consent fields, and the age-lock flag/keys) · expect: no remote doc from any collection contains those fields or values (walk every doc), the `prefs` docs hold none of the local keys (`onboarding.about`, `account.*`, notification keys), and `onboarding.basics` goes up without `birthYear`; the under-18 lock's storage (find where it lives) is classified local · must not: a field leaking through a new or nested key (a test walks every remote doc's JSON for the sentinel name and band).
- **SB5.1c** · What is backed up does come back · how: unit (two stores, one remote) · expect: fits (reading, score, fixes, occasion, look), closet pieces, outfits, wear log, Lookbook flags, the style profile (looks and fit only) and Kit's facts with their sources written on phone A are on phone B after the pull, row for row; B keeps its own name, age band and birth year when the pulled profile arrives · must not: A's name or age band reaching B.
- **SB6.1a** · Real holdings decide the path after a Welcome sign-in · how: unit (`afterSignIn` / the holdings reader over the memory remote) · expect: an account with fits → restore (age first); an account with no fits but a saved style profile with looks → restore too; only an account with neither → setup (`No fits saved…`); the counts are scored full checks only (re-checks not counted), live closet pieces, and whether a profile exists · must not: a profile-only account going to setup; re-checks counted as fits.
- **SB6.1b** · Under 18 stops and pulls nothing · how: unit/component (the restore flow over fakes) · expect: age under 18 → the age stop, no pull call, no row written to the phone, signed out, the under-18 lock set; 18 or over → the pull runs · must not: a pull before the age is known, or rows landing for a minor.
- **SB6.1c** · The restore pulls, counts as rows arrive, then skips setup · how: unit (restore over the memory remote with 5 fits and 3 pieces) · expect: the progress counts only go up and end at `5 fits · 3 pieces` (the screen's `{fits} fits · {pieces} pieces` format is words, not tested); when done onboarding is complete (`onboardingDone`), the setup steps are cleared, this phone's birth year and the age band he just picked are saved, and the privacy consent is not restored (the agreement still shows on the first camera open); a fits-restore ends with the "fits are back" result, a profile-only restore ends with the "profile is back" result and no counts line; a pull that can't reach the server gives a retry result and does not mark setup done · must not: setup marked done after a failed pull; the account's consent flags applied.
- **SB6.1d** · No backup round before the age question (added round 3, reviewer defect 1) · how: unit (`createBackup` with the new dep `ready()` over the memory remote holding an account's rows; a phone mid-Welcome: account saved, a fit of its own, no `sync.uid`) · expect: with `ready()` false (also when it returns a Promise) `syncNow()` is `'off'`, `connect` is never called, nothing is pulled (the phone has none of the account's fits or pieces), no row is written to the phone's store or to the remote (`syncRows` and `syncFiles` empty, remote writes and commits unchanged), `sync.uid` stays absent; the same with the under-18 lock set, including on a phone already joined (its new fit does not go up); when `ready()` turns true the next round is the normal first round (connects, pulls the account's rows, sets `sync.uid`, sends the phone's own) · must not: a pull or a connection while not ready; a minor's phone receiving the account's rows. The wiring of `ready` in `appBackup.ts` (the saved account with onboarding not done and no `sync.uid`; `getAgeBlocked()`) is not unit-tested here: it needs React Native and the Keychain (see below).
- **SB7.1-ids** · "Use the account's" uses the account's real fit IDs · how: unit/component (the sheet's choice path over a memory remote holding 3 account fits, a phone with 2 of those and 2 of its own) · expect: the ids passed as `inAccount` are exactly the account's 3 scored fit ids; after `useAccount` with the second confirm the phone's 2 own fits (and their re-checks) are gone and the account's 3 remain; if the account's ids can't be fetched (offline), nothing is deleted and the choice isn't offered as "ready"; Keep both merges (both sets exist afterwards, on the phone and on the server) · must not: `inAccount: []` ever reaching `resolveChoice` for a real account; any delete before the second confirm.
- **SB9.1a** · Delete runs revoke → server → phone, in that order, once each · how: unit (`deleteAccountAndData` over recording fakes for the Apple revoke, the server job and the wipe) · expect: an Apple account → call log is exactly `revoke, server, wipe`; a Google account → `server, wipe`; each exactly once · must not: any other order, a second server call, wipe before the server answered ok.
- **SB9.1b** · Offline or a server failure deletes nothing · how: unit · expect: server job offline → the call log ends after `server`, the store, files and Keychain are untouched, the result says offline (the line `Deleting your account needs a connection. Nothing was deleted.`); server failure → same, the result offers Try again, a second attempt runs the whole order again; the Apple revoke failing or Apple's sheet cancelled → `server` is never called and nothing is deleted · must not: any phone data deleted when the server step didn't succeed; the account signed out locally when it failed.
- **SB9.1c** · The under-18 lock stays after a delete, and the server's per-phone count stays · how: unit + emulator · expect: a phone locked under 18 stays locked after `deleteAccountAndData` (the age flag is untouched), and a delete never un-signs the lock; in the emulator, `deleteEverything(uid)` removes `users/{uid}` docs and files, `usage/{uid}` and the Auth user and leaves a seeded `devices/{hash}/usageDays/{day}` doc in place · must not: the lock cleared; the device count removed.
- **SB9.1d** · The server delete is complete and safe to run twice · how: emulator · expect: with docs in several collections, files in `photos/closet/scans`, a usage doc and an Auth user for A, and the same for B, `deleteEverything(A)` leaves nothing of A and all of B; running it again succeeds; the callable refuses a signed-out caller · must not: touching B.
- **SB-GATE** · Nothing backs up or restores with `ACCOUNTS_BUILT` off, for a guest or while signed out · how: unit · expect: with the real flag (false) the engine never starts or records; with it on, an anonymous (guest) Firebase user, a signed-out phone and a different user than the saved account push nothing and call no server · must not: a write for a guest.
